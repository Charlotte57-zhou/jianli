# Case Study: Multi-round AI PM Resume Evolution

This is an anonymized case distilled from a real resume optimization process. Direct personal identifiers are removed.

## Candidate profile

- Early-career candidate.
- Computer Science bachelor from a 211 university.
- Enterprise software background in electricity/finance settlement.
- Worked on large public-utility enterprise projects.
- Transitioning toward AI Product Manager.
- Built two personal AI projects:
  - an exception-handling Agent product;
  - an observable Coding Agent harness.

## Phase 1 — The first problem: “impressive” claims were too aggressive

An early draft contained claims like:

- “led the 26-province distributed settlement system”;
- “supported 120 billion RMB annual settlement”;
- “saved 60 million sheets of paper annually”;
- “built a configurable rule engine”;
- “modeled national differentiated subsidy policies”;
- “owned the subsidy funding application/allocation flow.”

Fact review found several issues:

- the candidate deeply participated in the 26-province system, but did not create the whole system from 0→1;
- the 120 billion figure came from public platform data, not verified module data;
- “60 million sheets saved” was an estimate derived from document count;
- the actual system used selected rules / hard-coded identifiers, not a productized configurable rule engine;
- only some provinces had special cases, not a national differentiated-policy engine;
- subsidy funding application/allocation belonged to another intersecting system.

### Lesson

Fact correction often makes a resume **stronger**, because the remaining numbers become defensible.

## Phase 2 — Identify the truly strong facts

Verified strengths included:

- business coverage across 26 provincial operating regions;
- roughly 3 million business-invoice relationships per month;
- at least another 3 million payment applications per month;
- candidate truly led the paperless capability from 0→1;
- multi-month on-site implementation experience;
- complex finance rules and cross-system data mapping;
- independent PRD/prototype/process/data mapping ownership in defined scopes.

The paperless bullet changed from an estimated outcome:

> saved 60 million sheets/year

to a defensible scale metric:

> paperless generation and archiving covered at least 6 million high-frequency business documents per month.

### Lesson

**Scale is a valid metric. ROI is not mandatory.**

## Phase 3 — Separate work experience from project experience

The employer summary became shorter.

Detailed project content moved into Project Experience.

This created two levels:

- company/role level: what kind of work the candidate did;
- project level: where the strongest evidence lives.

### Lesson

Do not make Work Experience repeat every project detail.

## Phase 4 — AI project language was too technical

Early AI bullets used terms such as:

- Agent Harness;
- MCP;
- Eval;
- DeliveryContract;
- worktree;
- SDK.

A nontechnical recruiter could not quickly understand the product value.

The rewrite changed the order:

1. what problem;
2. what AI does;
3. what remains deterministic/human-controlled;
4. how the result is verified;
5. technical implementation detail.

### Lesson

Use **plain-language first, technical proof second**.

## Phase 5 — Codex / Claude Code moved from “tool list” to capability

Instead of:

> Tools: Codex, Claude Code.

the resume described a work mode:

> uses AI coding agents to break business requirements into pages, features, development tasks and acceptance criteria; collaborates with them to build runnable prototypes/POCs, iterate functions, inspect code changes and run automated tests.

### Lesson

A tool name is weak. A repeatable working method is strong.

## Phase 6 — JD keywords

The team considered market keywords such as:

- AI Agent;
- LLM;
- workflow;
- Tool Calling;
- Eval;
- POC / Demo;
- AI Coding;
- B2B;
- 0→1.

The rule was not to add every common term.

Only terms supported by real evidence were retained.

### Lesson

**Keyword coverage must remain evidence-backed.**

## Phase 7 — Education moved up, but the first implementation failed

The 211 Computer Science education line was moved to the top, but initially rendered as small, low-contrast gray text.

The candidate correctly observed:

> “Who will even notice this?”

The design was revised:

- readable size;
- bold school name;
- 211 emphasized with text weight/color, not a decorative bubble.

### Lesson

**Information position and visual weight must agree.**

## Phase 8 — GitHub link strategy

A reviewer suggested removing the raw GitHub link from the top.

The final reasoning:

- the candidate is applying for product roles;
- a raw repo can cause a technical interviewer to evaluate engineering craftsmanship before understanding product context;
- the product demo is a better first-layer artifact;
- source code remains available during interviews.

### Lesson

Links should support the desired evaluation dimension.

## Phase 9 — Remove “not launched” from the title, keep status honesty

A personal Agent project was originally titled:

> Personal project, not launched.

The label “personal project” already established its nature.

“Not launched” created a negative first impression without adding useful information.

It was removed from the heading, while the body continued to avoid any production/customer claims.

### Lesson

Omitting a negative label is acceptable; implying false production impact is not.

## Phase 10 — Correct employer / client platform ownership

A line originally made the client’s shared-finance platform sound like the employer’s own product.

The structure was corrected:

- Employer = software vendor;
- Client platform = a large enterprise shared-finance platform;
- Modules = distributed settlement, renewable subsidy, extra-price fund;
- Candidate contribution = product work.

### Lesson

Enterprise project resumes must communicate organizational ownership correctly.

## Phase 11 — Group repeated platform projects

Instead of repeating:

> Enterprise Shared Finance Platform | Distributed Settlement
> Enterprise Shared Finance Platform | Renewable Subsidy
> Enterprise Shared Finance Platform | Extra-price Fund

the resume used:

> **Enterprise Shared Finance Platform**
> - Distributed Settlement
> - Renewable Subsidy Calculation & Settlement
> - Extra-price Fund Accounting

No extra “Product Manager” line was added under each module because the work experience had already established the role.

### Lesson

A project group heading can communicate depth and reduce visual noise.

## Final distilled principles

1. Start with evidence, not wording.
2. Position strongly, claim conservatively.
3. Use metrics that can survive interview cross-examination.
4. Treat JD keywords as evidence labels, not decorations.
5. Make first-screen signals visible.
6. Write AI product value in business language first.
7. Present AI Coding as a workflow capability.
8. Decide links based on evaluation strategy.
9. Distinguish personal-project evidence from production evidence.
10. Preserve employer/client/platform/module boundaries.
11. Group related modules instead of repeating the same platform.
12. Evaluate human feedback dialectically rather than following it blindly.


## Phase 12 — From one “universal” resume to master + tailored versions

A reviewer raised an important point:

> Keep a general base resume, but optimize a separate version for each real company and JD so the reviewer can quickly see similar experience and faster ramp-up potential.

This was adopted with one modification.

The goal is **not** to make the candidate a “万能型” generalist. Instead:

1. keep a complete master evidence base;
2. for each JD, foreground directly similar experience;
3. use adjacent problem structures next;
4. abstract reusable capabilities only as a bridge.

Example abstraction:

> Electricity settlement exception handling
> → rule-heavy, cross-system, auditable B2B exception workflow
> → transferable capability in workflow decomposition, responsibility mapping, and human-controlled AI investigation
> → relevant to finance reconciliation, compliance operations, and enterprise Agent products.

The recruiter-facing filename can also encode the application context:

> Candidate-Company-Role-Resume.pdf

while internal version numbers remain private.

### Lesson

A strong resume system is not “one perfect resume.”

It is:

> **one evidence base + many truthful, role-specific views.**
