# 招聘表达层

## 目标

招聘表达层把已经核验的职业证据翻译成招聘方能快速理解、面试官愿意追问、候选人能够回答的简历语言。它不负责判断事实真假，也不能提高能力所有权或项目验证阶段。

> 内部事实边界决定措辞强度，但内部审计语言不能泄漏到正式简历。

## 单向数据边界

### 内部层

仅供判断：

- `evidence_class`
- `ownership_level`
- `claim_risk`
- `personal_boundary`
- `missing_evidence`
- `validation_maturity`
- `interview_risk`
- `unsupported_scope`

### 外部层

允许进入正式简历：

- `recruiter_readable_claim`
- `project_context`
- `candidate_action`
- `observable_behavior`
- `scale`
- `evidence`
- `value`
- `target_role_language`

渲染器只读取外部层。内部层只负责选择、降级、删除或约束措辞。

## 转换顺序

每段经历先完成内部分析：

1. **项目或业务全景**：谁遇到了什么问题，项目处于什么系统或业务环境；
2. **候选人个人职责**：候选人明确负责的范围；
3. **关键动作**：候选人实际做出的决定、设计、协调、修改或验证；
4. **可观察能力**：这些动作体现了什么可复用工作行为；
5. **价值**：解决了什么用户、业务、产品或工程问题；
6. **结果证据**：交付物、数字、测试、Eval、反馈、试点或生产证据；
7. **内部事实边界**：没有负责、没有证明或不能归属的范围；
8. **招聘方可见表述**：自然、具体且不超过事实边界的表达。

第 7 项默认不直接输出。可以让“没有生产验证”把措辞限制在“完成 Demo 与离线评测”，不能生成“个人边界：项目没有上线”。

## 招聘方理解成本

每条候选表述检查：

1. HR 能否在缺少内部背景时看懂？
2. 招聘经理能否据此提出具体追问？
3. 候选人能否用证据回答？
4. 是否只有能力标签，没有可观察行为？
5. 是否只有技术名词，没有产品或业务意义？
6. 是否需要过多行业黑话才能理解？

记录六个内部维度：`clarity / relevance / evidence / specificity / defensibility / jargon_cost`。这些评分不进入正式简历。

## 能力必须落到行为

使用：

```text
能力原语 → 可观察行为 → 项目证据
```

不要只写“复杂系统建模能力”。应写候选人如何沿数据来源、责任边界、状态变化和异常回退路径梳理流程，以及形成了什么规则、映射或验收结果。

## 最终语言

- 自然表达，不显示内部字段名；
- 一条要点只承担一个主要招聘判断；
- 先写问题和个人动作，再写技术名词；
- 需要说明阶段时使用“探索性项目、POC、内部验证、离线评测”等正常招聘语言；
- 不用“未冒领、不是 Owner、不包装为、个人边界”等审计报告式语言。
