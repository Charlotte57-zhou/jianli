# 简历要点编译器

## 为什么需要编译

不要从原始经历直接生成一句漂亮的话。先核验事实和个人贡献，再选择能力、价值、证据与目标岗位语言。

```text
原始经历
→ 事实与证据审计
→ 候选人动作
→ 可观察行为
→ 职业能力
→ 价值
→ 结果证据
→ 目标 JD
→ 招聘方可读要点
```

## 编译约束

1. 每个事实只能来自职业证据库；
2. 动词强度不能超过个人贡献与能力所有权；
3. 项目阶段不能超过验证成熟度；
4. 技术词必须服务于可理解的问题或机制；
5. 内部审计字段不能进入输出；
6. 不跨独立项目拼接动作、数字或结果；
7. 同类项目可以归组展示，但每个独立项目必须仍可识别，或在定制差异记录中说明不展示原因。

## 五类常用模式

### 复杂 B 端

```text
业务问题 + 候选人动作 + 规则/状态/数据/权限机制 + 规模或交付证据
```

### AI 产品

```text
用户问题 + 为什么使用 AI + Rule/Workflow/Agent/Human 边界
+ 产品机制 + 验证证据
```

### 技术产品

```text
系统问题 + 设计机制 + 关键约束 + 测试/稳定性/交付证据
```

### 0→1

```text
起始状态 + 候选人明确负责范围 + 设计/推进动作 + 可验证交付
```

### 跨行业迁移

```text
原始具体场景 + 相似问题结构 + 有证据的可迁移能力
```

这些模式是内部组织工具，不要求最终要点使用相同句式，也不显示“背景、职责、结果”等标签。

## 独立项目保全

压缩表达不等于删除证据。每个项目必须有唯一项目标识，最终只有三种去向：

- 独立展示；
- 在平台或项目组下归组展示，并保留子项目名称与独立贡献；
- 因目标 JD 或篇幅有意不展示，并写入内部 `tailoring-delta.md`。

禁止把两个相似项目合成一个虚构项目，也禁止只保留其中较大的项目而让另一个静默消失。
