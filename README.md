# 简历证据库 3.1.0

> **将经过核验的职业证据，转化为招聘方看得懂、岗位匹配、面试可防守的定制简历。**

这是一个面向中文求职者的开源 Skill。

它不是把普通经历“包装得像大厂项目”，也不只是替你润色几句话。它会先帮你弄清楚：

- 这件事是不是真的；
- 其中哪些是你做的；
- 你真正掌握到了什么程度；
- 项目验证到了哪一步；
- 哪些能力适合目标岗位；
- 怎样写成招聘方一眼能理解、面试官可以追问、你自己能够回答的简历。

## 为什么普通简历优化经常失效

很多简历的问题不在文笔，而在中间缺了两层：

1. **招聘表达**：真实经历怎样翻译成招聘方熟悉的语言；
2. **简历交付**：内容怎样变成结构清楚、可编辑、可打印的正式文件。

直接从原始经历跳到“漂亮句子”，容易出现：

- 把参与写成主导；
- 把团队成果写成个人成果；
- 把 Demo 写成生产价值；
- 把 AI 生成的项目写成独立全栈开发；
- 把平台规模写成个人业绩；
- 简历里出现“不是 Owner、待验证、个人边界”等内部审计语言；
- 为了压成一页，把独立项目合并到直接消失；
- 技术词很多，但 HR 看不懂解决了什么问题。

简历证据库 3.1 就是为了解决这些问题。

## 它由三个系统组成

### 1. 职业证据引擎

回答：**你真正做过什么、掌握了什么？**

它会核对：

- 公司、客户、平台、模块和个人贡献；
- 公开数据、内部数据和估算数据；
- 候选人、团队与 AI 分别做了什么；
- 能力掌握程度；
- 项目验证阶段；
- 每条重要表述的面试风险。

### 2. 招聘表达引擎

回答：**怎样让招聘方快速看懂你的价值？**

每段经历会先按以下顺序进行内部整理：

```text
项目或业务全景
→ 个人职责
→ 关键动作
→ 可观察职业能力
→ 业务 / 产品 / 系统价值
→ 结果证据
→ 招聘方可读表述
```

能力不能只停留在标签。

不好：

> 擅长复杂系统建模。

更好：

> 沿数据来源、责任边界、状态变化和异常回退路径梳理跨系统流程，并将其转化为产品规则、字段映射和验收场景。

### 3. 简历渲染器

回答：**怎样把内容稳定交付成正式简历？**

当前内置两个原创 HTML 模板：

- **简洁专业版**：适合产品、运营、业务和多数中文社招；
- **高密度技术版**：适合 AIPM、AI、Agent、研发和技术产品岗位。

两个模板都支持：

- 可编辑 HTML；
- A4 打印；
- PDF 导出；
- 中文字体回退；
- 自然分页；
- 打印时隐藏工具栏；
- 默认不显示证件照区域。

内容超过一页时，优先使用两页，而不是疯狂缩小字号。

## 完整工作链路

```text
具体经历
→ 深度访谈
→ 找到重复出现的稳定行为
→ 核验事实与证据
→ 判断能力掌握程度
→ 建立职业证据库
→ 确定职业定位
→ 匹配目标 JD
→ 选择最可防守的内容
→ 翻译成招聘语言
→ 选择简历信息结构
→ 生成 HTML / PDF
→ 准备面试追问证据
```

## 3.1 最重要的两条硬规则

### 内部事实决定怎么写，但内部审计语言不能进入正式简历

内部可以记录：

```text
不是完整项目 Owner
缺乏生产验证
后续环节由其他同事负责
```

这些信息会限制简历的动词和结果强度，但正式简历不会出现审计报告式表达。

正式简历可以自然写成：

> 负责前期方案设计、接口字段、数据映射及流转关系梳理，完成可运行 Demo 与离线评测。

### 压缩表达不等于删除证据

合并同类项目时，不允许让独立项目直接消失。

每个项目只有三种去向：

1. 独立展示；
2. 放在同一平台下归组展示，但保留子项目名称和独立贡献；
3. 因目标岗位或篇幅暂不展示，并在内部定制记录中说明原因。

职业证据库和母版始终保留原始项目。

禁止把两个项目的动作、数字和结果拼成一个更厉害但并不存在的新项目。

## 不只是“性格分析”

“好奇心强、学习能力强、责任心强、沟通能力强”可能都是真的，但不能直接证明你适合某个岗位。

系统会完成：

```text
自然倾向
→ 可观察行为
→ 职业能力
→ 项目证据
```

例如：

```text
“容易发现哪里不对”
→ 主动比较数据来源、页面状态和真实业务结果
→ 异常与不一致识别
→ 实际缺陷、对账、验收或 Bad Case 证据
```

只有到最后一步，才可能成为简历中的职业能力。

## 判断你真正掌握到了哪一步

| 等级 | 掌握程度 | 可以怎样表达 |
|---|---|---|
| L0 | 接触、看过或参与过 | 接触、了解、参与 |
| L1 | 借助 AI 做出结果，但解释和修改有限 | 借助 AI 完成初版或原型 |
| L2 | 能解释核心流程、设计逻辑和个人决策 | 定义、设计或负责明确范围 |
| L3 | 能修改关键内容、定位问题并完成 Debug | 修改、调试、迭代关键链路 |
| L4 | 能独立复现核心过程，并设计验证和失败处理 | 独立复现或构建真实范围 |
| L5 | 达到 L4，并经过真实使用、试点或生产验证 | 写明真实验证过的对应范围 |

项目上线不代表候选人自动达到 L5；候选人能复现项目，也不代表已经产生业务价值。

## AI 辅助项目怎么判断

借助 Codex、Claude Code、Cursor 等工具做出项目，不等于项目中的全部能力都属于候选人。

系统会继续检查：

```text
解释
→ 修改
→ Debug
→ 复现
→ 验证
```

还会追问：

- 为什么这样设计？
- 为什么不使用其他方案？
- 核心数据流是什么？
- 为什么需要 Agent？
- Rule、Workflow、Agent 和人工确认如何分工？
- 成功指标是什么？
- 失败或证据不足时怎么办？
- 核心调用链是什么？
- 主要 Bad Case 是什么？

解释权不足时，先补项目理解和验证，不继续强化简历表述。

## 区分项目验证阶段

```text
想法
→ 原型
→ 可运行 Demo / POC
→ 离线 Eval
→ 用户访谈或专家评审
→ 小范围试点或真实使用
→ 生产环境
→ 已测量的业务结果
```

简历只能写到真实达到的阶段：

- Demo 不等于真实用户价值；
- 离线 Eval 不等于生产效果；
- 生产环境不等于已经证明业务收益；
- 业务结果必须说明指标、统计范围、时间和归属。

## 针对 AIPM

AIPM 项目默认按照这个顺序表达：

```text
业务或用户问题
→ 为什么需要 AI
→ 哪些环节不用 AI
→ AI 边界
→ 产品机制
→ 人工控制
→ 验证
→ 证据
→ 第二层技术证明
```

不会第一句话就堆叠 MCP、Harness、Tool Calling、Agent Eval 等术语。

先让招聘方明白解决了什么问题，再用技术机制证明候选人的产品判断和实现理解。

使用 AI Coding 时，默认优先表达为：

> **AI 原生产品构建、检查和验收能力。**

只有具备更强的独立实现、复现和验证证据时，才使用独立开发类表述。

## 你最终可以得到什么

- 事实与证据清单；
- 能力掌握程度清单；
- 职业能力库；
- 职业定位审计；
- 完整母版简历；
- 针对目标岗位的定制简历；
- 招聘方可读的项目与经历表述；
- 独立项目去向记录；
- 面试证据卡；
- 可编辑 HTML；
- A4 / PDF 打印检查结果。

内部审计文件默认不会作为正式简历发送给招聘方。

## 安装

### 方法一：下载仓库

在 GitHub 点击 `Code → Download ZIP`，解压后找到：

```text
skill/jianli
```

将整个 `jianli` 文件夹复制到：

```text
Windows：%USERPROFILE%\.codex\skills\jianli
macOS / Linux：~/.codex/skills/jianli
```

重新打开 Codex 后输入 `$jianli`。

### 方法二：Git 克隆

```bash
git clone https://github.com/Charlotte57-zhou/jianli.git
```

然后复制仓库中的 `skill/jianli` 到本地 Skills 目录。

## 可以直接复制的提问方式

### 探索优势与定位

```text
请使用 $jianli 对我进行深度访谈。一次只问一个具体问题，从真实经历中识别稳定行为、职业能力、掌握程度和证据边界。先完成定位审计，不要直接写简历。
```

### 优化现有简历

```text
请使用 $jianli 审查这份简历。先核验事实、个人贡献和项目阶段，再匹配目标 JD，通过招聘表达层生成正式简历。内部审计语言不要进入成稿，压缩时不要丢失任何独立项目。
```

### 审计 AI 项目

```text
请使用 $jianli 审计我的 AI 辅助项目，检查我能否解释、修改、Debug、复现和验证，区分我的贡献与 AI 贡献，再给出可防守的简历表述。
```

### 求职 AIPM

```text
请使用 $jianli 和 AIPM 岗位包，先讲业务问题、AI 边界、人工控制和验证，再补充 Agent、MCP、Eval 等技术证明，最后生成高密度技术版 HTML 简历。
```

### 生成简历文件

```text
请使用 $jianli 先选择适合我的简历信息结构，再生成可编辑 HTML，并检查 A4、分页、中文字体、打印工具栏和 PDF 文本复制。没有照片时不要生成空照片框。
```


## 开源贡献原则

欢迎贡献岗位知识、匿名案例、表达模式和原创 Renderer，但必须保持：

- 不写入候选人的真实姓名、电话、邮箱或雇主敏感信息；
- 不把个人经验描述成统一招聘标准；
- 不削弱“增强定位，但不增强事实”；
- 不让内部审计语言进入正式简历；
- 不因压缩而删除独立项目；
- 不复制其他项目的模板代码、文案、品牌或资源。
